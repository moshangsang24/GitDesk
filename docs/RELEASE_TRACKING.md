# 发布流转追踪

M4 提供只读试用。发布流转追踪回答指定提交是否已出现在当前仓库用于测试、预生产或正式环境的分支历史中。输入来自本机 Git 仓库，显示的是提交包含证据，可用于核对提测或发布前的提交清单。部署、MR 和 CI 的实际状态由各自系统确认。

## 配置目标分支

在仓库的 **Releases → Configure targets** 中，为 Test、Staging、Production 分别选择一条已存在的远程跟踪分支。配置按逻辑仓库保存，同一仓库的多个 worktree 共享。仓库有对应引用时，可建议 `origin/test`、`origin/staging`、`origin/master`，由用户确认。可以选其他远程和实际分支，例如 `upstream/test/20261124`。每个阶段独立判断，可以只配置有用的阶段，也允许提交跳过 Test 直接进入 Production。

配置保存精确的 `refs/remotes/<remote>/<branch>`。排除 `origin/HEAD` 一类别名，引用缺失时显示实际缺失项。更换轮次时显式选择新测试分支。目标变更递增配置版本，旧目标的结果保留在历史观察中，新目标根据自己的 tip 重新计算。

## 用任务追踪一组提交

1. 在 History 选择一条或多条提交，使用 **Track as task**。也可以在 **Releases → Add task** 从一个任务分支生成候选。任务保存标题、可选任务号、来源分支或 worktree，以及确认后的完整提交 OID 清单。清单去重且不能为空。
2. 按分支生成候选时，先确认 base 和 head 的完整 OID，输入框可从引用目标中选择。用 `git log --topo-order --no-merges <base-oid>..<head-oid>` 列出最多 200 个候选，展示提交标题、作者和截断提示。同步其他分支带入的提交也可能出现，由用户勾选和增删。需要追踪 merge commit 自身时，可从 History 显式添加。
3. 保存后始终按已确认的清单计算。源分支继续提交、被合并或删除后仍可查看任务。新增提交或 rebase 后替换提交时，先预览新旧清单，再保存为任务的新版本。归档后仍可查看证据，确认删除只移除 GitDesk 内的任务记录。

未提交的修改需要形成提交后才能加入任务。点击阶段单元格可以核对已包含、未包含和无法判断的提交，打开提交详情或定位 History。目标提交超出当前历史范围时，沿用 History 的范围切换提示。

## 证据和状态

每次读取冻结逻辑仓库、配置版本、任务版本、待判断 OID、各阶段精确引用及其提交 tip。对每一对完整 OID 运行 `git merge-base --is-ancestor <commit-oid> <tip-oid>`。读取完毕后再次核对当前 tip 和请求版本。若某阶段的引用变化，丢弃该阶段本轮结果并有限重试。其他阶段仍可返回各自的有效结果。观察时间记录本机读到引用的时刻。

| 单提交状态 | 含义 |
| --- | --- |
| 已包含 | 退出码 `0`，已证明原提交是目标 tip 的祖先，或就是该 tip |
| 未包含原提交 | 退出码 `1`，且当前历史足以得出否定结论 |
| 无法判断 | 浅克隆中的否定结果、对象缺失、超时、Git 错误等，详情显示原因 |
| 计算中 | 已排队或正在计算，当前还没有结论 |
| 未配置 / 引用缺失 | 阶段没有目标，或已保存的目标引用在本机消失，提示配置或刷新 |

任务单元格按阶段显示 `已包含数 / 任务提交数`，详情分列未包含、无法判断和计算中的条目。全部已包含时显示「已包含」。部分已包含时显示「部分包含」，未知项仍单独标明。只有所有提交均被证明未包含时，才显示「未包含原提交」。尚无已包含时，优先显示「计算中」，待计算结束后如仍有未知项则显示「无法判断」。目标未配置或引用缺失时，优先显示阶段状态。

普通 merge 和 fast-forward 会保留原提交 OID。Cherry-pick、rebase 和 squash 可能引入新 OID，因此「未包含原提交」后仍可能需要人工核对补丁。Revert 后原提交仍可在祖先历史中出现。Releases 只报告本机 Git 观察到的历史包含关系。

## 刷新与历史观察

- 显示本机引用观察时间和所选远程最近一次由 GitDesk **成功 Fetch** 的时间，两者分别记录。手动刷新重读本机引用。外部 Fetch 被观察到后，更新本机观察时间。GitDesk Fetch 记录缺省显示「未记录」。
- 工具栏的显式 Fetch 成功后刷新关联阶段的本地证据，并按远程保存成功时间和 refspec。Pull 只 Fetch 当前分支的 upstream，因此独立于该记录。失败时保留上次有效证据并显示「过期」和失败原因。无可用本地证据时显示无法验证。由于使用本地跟踪引用且 Fetch 不自动 prune，即使 Fetch 成功，也需要说明某个目标可能未被 refspec 覆盖，或已在服务器删除但仍留在本机。
- 「历史观察」记录已计算的有效快照，包含实际目标、tip OID、任务版本、观察时间和逐提交证据。目标、tip、任务版本或证据变化时新增记录，相同结果去重。每个任务每阶段最多保留 50 条，每个仓库共保留最近 750 条。切换测试分支、任务改版及 force-update 后可回看旧记录。对象被 Git 清理后，当前证据按实际可用性判断。观察时间可用于回溯本机曾看到的状态。

## 数据与执行约束

| 对象 | 关键字段与用途 |
| --- | --- |
| `ReleaseProfile` | `repoId`、`targetRevision`、`test` / `staging` / `production` 到远程名及精确 ref 的映射 |
| `TrackedTask` | `repoId`、`taskId`、标题、可选任务号及来源、可选 base/head OID、非空去重的 `commitOids`、`taskRevision`、归档状态 |
| `StageSnapshot` | 阶段、实际目标、tip OID、`observedAt`、可空的 `lastAppFetchAt`、过期标记及原因 |
| `ReleaseEvaluation` | 目标版本、可选任务版本、分阶段快照与逐提交状态。仓库和请求 ID 由对应 IPC 关联 |

时间字段使用 Unix 毫秒。配置和任务按 `RepoId` 读写，采用带预期版本的类型化 GitService/IPC。保存只写 GitDesk 本地数据，沿用原子写入，保留有限的修订和观察元数据。任务删除前须确认。新配置没有已确认的目标时，显示未配置。详细存储和执行约束见 [技术架构](ARCHITECTURE.md)。

每仓库最多保存 100 个任务，每任务最多跟踪 200 个提交并保留最近 10 个旧清单版本。Releases 顺序计算当前筛选下的任务，表格每页 12 个。History 按可见行分批计算，滚动时取消过期请求。同一次计算复用相同 tip 的结果。批量图遍历可证明遇到的 OID 已包含，未遇到的 OID 继续使用精确查询。切换仓库、任务或目标后，只显示匹配当前版本的证据。

## 实施与验收

M3 提供真实 History 和可定位的提交。M4 的独立工作实现目标配置、逐提交证据、任务聚合、历史观察和界面。M5 已接入显式 Fetch，M6 进行 P0 发布验收。Workspace 目标模板、跨仓库总览和补丁等价候选可后续评估。补丁候选需单独标记证据来源，不计入已包含数。页面与状态显示见 [交互规范](DESIGN_SYSTEM.md)。

- 用临时仓库覆盖普通 merge / fast-forward、部分包含、跳过阶段、回退目标 tip、目标缺失、切换测试分支、浅克隆和对象缺失。覆盖 cherry-pick、rebase、squash、revert，核对界面文案与原 OID 的真实结果。
- 验证候选含有同步带入的提交、源分支删除、任务改版、归档恢复、历史记录上限，以及两个 worktree 共用同一仓库配置。验证迁移保留现有工作区、仓库移除记录和选择。
- 验证本地刷新不联网，分别用本地 bare remote 测试显式 Fetch 成功、失败和 refspec 未覆盖。检查操作前后的仓库 refs、工作区和对象库。切换仓库、目标、任务或分页时，验证旧响应被正确丢弃。
- 以至少 100 个追踪任务验证有界调度。开关本地/远程引用标签、切换 History 范围及加载页时，同一提交对同一目标 tip 的证据保持一致，图的列布局和滚动不受异步证据更新干扰。
